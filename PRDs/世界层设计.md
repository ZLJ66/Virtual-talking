## 一、设计目标与边界

### 1.1 问题诊断：五个痛点不在同一层

讨论中确认的五个痛点，本质分属三个不同层。**这是本次设计最重要的框架性结论**——把不同层的问题混在一起，会导致"选哪个方案都觉得缺了点什么"。

| 痛点 | 所属层 | 解法 |
|---|---|---|
| 场景之间像关卡，没有"同一个世界"的连续感 | 世界层 | 地点图 + 常驻 NPC + 持久状态 |
| 切换是系统决定的，玩家没有主动权 | 交互层 | "离开"变成玩家的动作 |
| 旁白/开场套路，没有代入感 | 生成层 | 具体化输入 + 约束 |
| NPC 像陌生人，记不住之前做过什么 | 世界层 | 印象标签 + 记忆 + 跨场景复用 |
| 每次玩都差不多，没有重玩价值 | 生成层 | 骨架固定、血肉随机 |

**方案 1（酒馆式）是世界层的答案，方案 2（随机场景）是生成层的答案。**二者回答的是不同问题，不构成二选一。

### 1.2 三层架构

```
┌─────────────────────────────────────────────────────────┐
│ 世界层（代码管理）                                        │
│ 地点图 · 世界时钟 · 主线节点 · 世界事实 · NPC 记忆与印象   │
│ 职责：维护"什么是真的"，AI 不得直接修改                    │
└────────────────────────┬────────────────────────────────┘
                         │ 注入上下文
┌────────────────────────▼────────────────────────────────┐
│ 生成层（AI 生成）                                         │
│ 旁白 · NPC 台词 · 英语反馈 · 状态变更提议                  │
│ 职责：把世界状态演出来，不决定世界状态                      │
└────────────────────────┬────────────────────────────────┘
                         │ 结构化输出 + 校验
┌────────────────────────▼────────────────────────────────┐
│ 交互层（保留现有资产）                                     │
│ 事件流 · 打字机 · 打断/暂停/请求重复 · 双语旁白 · 双输入框  │
│ 职责：呈现与输入，不关心世界结构                            │
└─────────────────────────────────────────────────────────┘
```

**关键约束：AI 返回的 `world_changes` 只是「提议」，代码校验通过后才生效。** 这继承现有工程纪律（[`MVP开发规划.md`](MVP开发规划.md) 第六章第 1 条）。

### 1.3 明确不做（本版本）

| 不做 | 理由 |
|---|---|
| 主持人调度器（方案 5） | 预留位置，仅在出现"AI 接不住"时引入。第七章兜底规则先覆盖已知情况 |
| 多世界（澳洲移民 / 旅行者） | 先做一个世界做深。`StoryBackground` 保留其余两项为占位 |
| 语音、图像、动画 | 沿用现有 MVP 边界 |
| 完全开放世界 | 地点是离散的、预先设计的，不做自由文本移动 |

### 1.4 MVP 范围重定义

**显式承认：本次扩展超出原 MVP 的 9 项清单。** 原规划将"开发范围膨胀"列为风险，对策是守住 9 项清单（[`MVP开发规划.md`](MVP开发规划.md) 1.3）。既然决定引入世界层，应当正式修订范围，而非假装仍在原范围内。

修订后的 MVP 范围（11 项，替换原清单第 2、3 项）：

| # | 功能 | 变化 |
|---|---|---|
| 1 | 基本角色设置 | 不变 |
| 2 | **一个世界 + 一条主线** | 替换"一个完整故事" |
| 3 | **8 个地点，可自由移动** | 替换"3~5 个生活场景" |
| 4~8 | 自由输入 / 动作输入 / 动态旁白 / 打断 / 英语反馈 | 不变 |
| 9 | 剧情自动保存 | 机制重写（见第八章） |
| 10 | **世界时钟与时段** | 新增 |
| 11 | **NPC 记忆与印象标签** | 新增 |

## 二、世界圣经

世界圣经是内容生产的第一份文件，**不先写它，后续每个地点都会不一致**。

### 2.1 基本信息

```yaml
world:
  id: uk_first_week
  title: 在英国的第一周
  year: 2025                    # 必须锁定，见 2.4
  meta:
    country: 英国
    city: 曼彻斯特（虚构街区 Ashworth）
    season: 九月初，开学季
    weather: 阴，偶有阵雨，傍晚转凉
    currency: GBP
    language_env: en-GB
    timezone: BST
  player_start:
    location: dorm
    time: { day: 1, slot: morning }
    inventory: [两个行李箱, 护照, CAS 信, 手机]
```

### 2.2 语气基调

> 日常写实，温和，不狗血。世界不对玩家怀有恶意，也不刻意讨好。
> NPC 是普通人：会忙、会走神、会记错、也会热心。没有人专门等着考玩家的英语。

### 2.3 世界规则

```yaml
rules:
  - 这是一个日常向世界，不存在超自然、犯罪、暴力情节
  - 玩家不会因为英语表达不好而被惩罚、被拒绝服务或被赶走
  - NPC 会猜测意图、请求澄清、主动帮助，就像现实中遇到外语不流利的人
  - 政策与流程以 2025 年为准（eVisa / share code 已取代 BRP 实体卡）
  - 玩家可以完全无视主线自由活动，世界不会因此中断或惩罚
  - 时间只被「移动」消耗，对话与思考不消耗时间

taboos:
  - 不出现暴力、犯罪、歧视、性相关内容
  - 不在旁白或台词中评判玩家的英语水平
  - 不出现"练习""考试""评分"等打破沉浸的词汇
```

### 2.4 年份必须锁定

**理由（来自实证研究）：** BRP 实体卡已于 2025 年 1 月 1 日被 eVisa 取代，留学生现在出示的是 **share code**（90 天有效），而非实体卡（[gov.uk](https://www.gov.uk/evisa/view-evisa-get-share-code-prove-immigration-status)）。

不锁年份，内容会过时，**而且过时得很隐蔽**——场景照常运行，只是不再真实。世界圣经必须在开头声明年份，所有涉及政策的场景以此为准。

## 三、世界地图与主线

### 3.1 地点图（8 个）

```
                    ┌──────────┐
                    │ 宿舍 ★   │ ← 起点，永远可达（兜底锚点）
                    └────┬─────┘
          ┌──────────────┼──────────────┐
          │              │              │
    ┌─────▼─────┐  ┌─────▼─────┐  ┌────▼──────┐
    │ 便利店    │  │  公交站   │  │  超市     │
    │ (24h)     │  │  (枢纽)   │  │           │
    └───────────┘  └─────┬─────┘  └───────────┘
                         │
          ┌──────────────┼──────────────┐
          │              │              │
    ┌─────▼─────┐  ┌─────▼─────┐  ┌────▼──────┐
    │ 注册处 ★  │  │  银行 ★   │  │ 咖啡馆    │
    └─────┬─────┘  └───────────┘  └───────────┘
          │
    ┌─────▼──────┐
    │ 导师办公室★│
    └────────────┘
```

★ = 主线相关。**宿舍是兜底锚点**：任何时候至少有一个可达地点（见 8.1）。

### 3.2 主线的真实因果链

**关键设计发现（来自对英国大学实际注册流程的研究）：主线不需要人造的关卡串联，真实的行政流程本身就是因果链。**

英国大学国际学生注册是一条真实的 10 步链（[考文垂大学注册指南](https://www.coventryuniversity.cn/enrolment/)、[QMUL 注册文件要求](https://www.qmul.ac.uk/newstudents/enrolment/enrolment-documentation/)）：

```
缴纳押金 → 获得 CAS → 申请签证 → 支付学费 → 备齐 RTS 材料
  → Enrolment Portal 线上注册 → 抵英领取签证凭证
  → Right to Study Check（线下，有日期窗口）→ 领取学生证
  → 领取在读证明 → 凭在读证明到银行开户
```

**其中两个关键事实：**

1. **RTS Check 有真实的日期窗口。** 考文垂 2024 年为 8 月 27 日 – 10 月 14 日。这是天然的主线截止时间，无需编造。
2. **银行开户需要学校开具的"在读证明"。** 学校链与银行链真实串联——这就是主线结构的来源。

### 3.3 主线节点定义

```yaml
mainline:
  title: 安顿下来
  deadline: { day: 5, slot: afternoon }    # RTS Check 窗口关闭

  nodes:
    - id: enrol_online
      title: 完成线上注册
      location: dorm
      requires: [cas_letter, passport]
      grants_facts: [pre_enrolment_submitted]
      soft_paths: [找室友借电脑, 去学校图书馆用公用电脑]

    - id: rts_check
      title: 通过 Right to Study 检查
      location: student_centre
      requires: [passport, share_code, cas_letter]
      grants_facts: [rts_check_passed]
      window: { day: 1, slot: morning } .. { day: 5, slot: afternoon }
      soft_paths: [先找导师说明情况, 联系 Student Centre 预约]

    - id: student_card
      title: 领取学生证
      location: student_centre
      requires: [rts_check_passed]
      grants_facts: [student_card_issued]
      soft_paths: []

    - id: bank_account
      title: 开设银行账户
      location: bank
      requires: [status_letter_obtained, passport, proof_of_address]
      grants_facts: [bank_account_opened]
      soft_paths: [换一家银行, 先办基础账户]
```

## 四、数据模型

> **本章是合同。** 改动本章的代价远高于改动其他章节。

### 4.1 总览

```
World
├── meta          世界元信息（含锁定年份）
├── rules         世界规则与禁忌
├── locations[]   地点卡
├── npcs[]        人物卡
├── mainline      主线定义（节点 + 截止）
└── (运行时) PlayerState
     ├── location, time, inventory
     ├── facts         世界事实（主线判定依据）
     ├── knowledge[]   玩家已知信息
     └── npc_states{}  每个 NPC 的印象标签与记忆
```

### 4.2 Location（地点卡）

```yaml
locations:
  - id: convenience_store
    name: 街角便利店
    name_en: Corner Shop
    open_hours: [0, 24]                  # 24 小时营业
    travel_cost: 1                       # 移动消耗的时段数
    connections: [dorm, bus_stop, supermarket]

    # ── 感官细节：生成层具体性的来源，至少 5 条 ──
    sensory:
      sight: 冷白灯管有一根在闪，货架第三层空了一格
      sound: 冰柜持续低鸣，门口迎宾铃每有人进出就响一声
      smell: 速溶咖啡和清洁剂混在一起
      touch: 门把手有点黏，暖气片是热的
      temperature: 比街上暖，玻璃上有一层薄雾

    # ── 时段变体 ──
    variants:
      morning: 店员在补货，过道上堆着没拆的纸箱
      afternoon: 附近中学放学，柜台前排队
      evening: 三明治只剩两个，关东煮的汤快见底
      night: 只有一个店员值班，安静得能听见冰柜声

    resident_npcs: [raj]

    # ── 持久化的地点状态 ──
    state_fields:
      sandwich_stock: 2
      umbrella_left: false
```

### 4.3 NPC（人物卡）

```yaml
npcs:
  - id: raj
    name: Raj
    role: 便利店老板
    age: 54
    background: 印度裔，来英二十二年，这家店开了十二年

    # ── 说话方式：直接注入 prompt，决定 NPC 是否"像个人" ──
    speech:
      style: 语速慢，句子短，不主动展开话题
      accent: 轻微印度口音，个别词会拖长
      catchphrase: mate
      register: 随意亲切，对熟客会多问一句

    personality: 话不多但观察力强。记得住每个熟客买什么。不喜欢寒暄，但会用行动表示关心。

    # ── 人设候选池（生成层"血肉随机"机制，见 6.3）──
    variants:
      - 五十四岁，开了十二年店，管所有客人叫 mate，收银时不太看人
      - 三十出头，刚接手父亲的店，还在学怎么和客人闲聊，有点用力过猛

    # ── 运行时填充 ──
    impression_tags: []      # 印象标签，见 4.4
    memories: []             # 记忆条目，见 4.5
```

### 4.4 印象标签（关系度的实现方式）

**设计约束（两条硬约束）：**

| 约束 | 理由 |
|---|---|
| **只由剧情选择和行为驱动，不由英语表达质量驱动** | 产品原则明确要求"用户即使表达不够自然，也不应被 NPC 惩罚"（[`产品文档.md`](产品文档.md) 1.3 硬约束 1）。若关系度由表达质量决定，等于用英语水平给玩家的人际关系打分，会让最需要鼓励的初级用户体验最差 |
| **用印象标签，不用数值** | 数值诱导刷分，且需要额外翻译才能进 prompt。标签本身就是 prompt |

**结构：**

```yaml
impression_tags:
  - "记得你第一天忘了拿找零，我追出去喊你"
  - "觉得你是个安静有礼貌的年轻人"
  - "知道你住附近，常来买三明治"
```

**更新规则：**

| 触发 | 示例 | 是否写入 |
|---|---|---|
| 剧情选择 | 帮室友搬箱子、主动道谢、记住对方名字 | ✅ |
| 重复行为模式 | 连续三次买同一种三明治 | ✅ |
| 玩家表达出错但意图清楚 | 语法错误的句子 | ❌ **不写入，也不扣减** |
| 玩家无礼 | NPC 可表现不悦（皱眉、停顿），但标签只记录事实，不做道德评判 | ⚠️ 记录行为，不记评价 |

**容量上限：每个 NPC 最多 8 条。** 超出时按"最近 + 最早"保留（最早的构成第一印象，最近的反映当前关系），中间的先淘汰。

### 4.5 NPC 记忆

**写入时机：** 每个回合结束后，代码从本回合事件中提取 0~1 条记忆。**不是每回合都写**——只有发生了"值得记住的事"才写。

**判据：**

| 值得记 | 不值得记 |
|---|---|
| 涉及世界事实变化（拿到了学生证） | 一次普通的寒暄 |
| 涉及玩家的选择（拒绝了店员的推荐） | 玩家重复问同一个问题 |
| 涉及情绪转折（玩家看起来很难过） | 常规的交易完成 |

**注入方式：** 与印象标签合并注入，不做区分（对 AI 而言两者都是"我知道关于这个人的事"）：

```
## 你认识的这个人
- 记得你第一天忘了拿找零，我追出去喊你
- 知道你住附近，常来买三明治
```

**容量上限：每个 NPC 最多 12 条记忆**，超出按时间淘汰最旧的。

### 4.6 世界时钟

```yaml
time:
  day: 1
  slot: morning
  slots: [morning, forenoon, noon, afternoon, evening, night]
  advance_rule: movement_only     # 仅移动消耗时段
```

**六时段划分：** 早晨 / 上午 / 中午 / 下午 / 傍晚 / 晚上。**不显示具体分钟**——有节奏感，但不逼玩家算时间。

**推进规则：**

| 行为 | 是否消耗时段 |
|---|---|
| 移动（跨地点） | ✅ 消耗 `travel_cost` 个时段 |
| 对话 / 输入 / 思考 | ❌ 不消耗 |
| 原地等待 | ✅ 消耗 1 个时段（玩家主动选择） |
| 打断 / 请求重复 | ❌ 不消耗 |

**关键后果（正面）：对话不消耗时间 = 练习不被惩罚。** 若对话消耗时间，英语越差的玩家越容易错过截止，等于用英语水平惩罚玩家。时间只被"移动"消耗，把两种资源分得很干净：

| 资源 | 消耗方式 | 效果 |
|---|---|---|
| 时间 | 只被移动消耗 | 选择有重量：去哪里、先办什么 |
| 对话 | 不消耗 | 玩家可以在银行里磕巴 20 分钟，世界不会扣分 |

**"原地等待"必须存在。** 否则玩家在错误时段到达某地，只能靠来回移动刷时间。等待 = 一个回合：世界推进一拍，可能有事发生（室友回来、电话响），也可能只是旁白描述时间流逝。**等待不是空转，是给世界一个机会。**

**时间流逝必须被叙述，而不是 UI 数字跳变。** 移动时结算，到达时呈现："你穿过两条街，天已经暗下来了。"

### 4.7 完整运行时状态样例

```yaml
  location: convenience_store
  time: { day: 2, slot: evening }
  companions: [sam]          # 跟着玩家移动的 NPC，随移动保留
  inventory: [护照, CAS 信, 手机, 学生证, 在读证明]
  facts:
    pre_enrolment_submitted: true
    rts_check_passed: true
    student_card_issued: true
    status_letter_obtained: true
    bank_account_opened: false
  knowledge:
    - "银行开户需要在读证明和地址证明"
    - "RTS Check 在周五下午关闭"
  npc_states:
    raj:
      impression_tags:
        - "记得你第一天忘了拿找零，我追出去喊你"
        - "知道你住附近，常来买三明治"
      memories:
        - "第二天晚上你又来了，买了同样的三明治"
        - "你问过我这附近哪里能开户"
```

#### 4.7.1 companions（同行者）

**问题**：早期实现里，NPC 只由 `location.resident_npcs` 决定。
玩家在宿舍约室友 Sam 一起去商店，到了商店 Sam 就消失了——
数据模型里根本没有「谁和你在一起」这个概念。

**设计**：

- `companions: list[str]` 存 NPC id，独立于地点。
- 「在场的人」= `resident_npcs ∪ companions`（去重）。
- 同行者不随地点切换消失，只有 AI 判定分别时才移除。
- 转场时把 `companions` 一并传给开场生成，旁白必须体现「一起走进来」，
  否则会出现「两人一起出发，进店后只剩一个人」的割裂感。

**AI 侧判定规则（实测决定，不可简化）**：

```python
# ❌ 这样写只有 3/8 的命中率
"- 当玩家邀请某人同行且对方同意时，加 add_companion。"
"- 不要滥用：随口一句 see you 不算同行。"

# ✅ 这样写 8/8 命中
"- 玩家说「一起走」「走吧」「带我去」这类话，且 NPC 回应里表示同意
   （出现 Let's go / Come on / Sure 等）→ 必须写 add_companion"
"- 两人一起往某个方向走、NPC 起身跟上 → 必须写 add_companion"
"- 只是「口头约定但没动身」→ 不写"
```

**教训**：给 LLM 写「不要滥用」这类负面约束，会让它倾向于**什么都不写**。
必须给出**可机械判断的正向条件**（说了什么话 → 对方怎么回应 → 就写），
而不是让它凭语感决定。实测产出率从 38% 提升到 100%。

#### 4.7.2 具体性检测的匹配方式

旁白具体性检测最初用 `re.findall(r"[\u4e00-\u9fa5]{2,6}")` 从感官细节里切词，
再要求这些片段原样出现在旁白中。这是错的——正则会贪婪地切出
「走廊尽头的窗」「户蒙着一层水」这类无意义片段，**几乎必然匹配失败**，
导致合格旁白被大量误报。

改为**二元组（滑动窗口）匹配**：只要旁白与感官细节共享一个
「有信息量的」二元组（排除虚词/量词）即视为命中。

**已知局限**：二元组对通用词没有免疫力。感官里写了「隔壁**房间**传来……」，
旁白只要出现「房间」就算命中，哪怕写的是「房间里安静极了」。
这种误判方向是**放过不具体的旁白**（漏报），代价可接受。
若将来要收紧，应改为维护「具体名词表」，而不是继续调二元组。

#### 4.7.3 记忆的写入通道与红线

**两条写入通道，缺一不可：**

| 通道 | 触发 | 为什么必须存在 |
|---|---|---|
| **代码直写** | 主线节点完成 | 「拿到了学生证」是世界事实。交给 AI 决定，它这一回合只要漏写，这次大事就永久缺席——玩家办成了事，在场的人却毫无印象 |
| **AI 提议** | 玩家做了选择、表了态、露出情绪、发生具体事件 | 这类事的判据是语义的（「说了想家」算，说了「谢谢」不算），代码判断不了 |

**AI 提议必须经过代码校验，不可直接写入。** 校验规则
（`backend/npc_memory.py`）：

| 拒收条件 | 原因 |
|---|---|
| 涉及英语表达质量（语法/用词/发音/口音/地道） | 《产品文档.md》1.3 硬约束 1：关系度不得由英语表达质量驱动 |
| 道德评判（没礼貌/粗鲁/差劲） | 设计文档 4.4：只记录行为，不记录评价 |
| 元词汇（玩家/用户/AI） | NPC 不会说「玩家」。出现即说明 AI 把第三人称分析写进了记忆 |
| 纯英文 | 会和其他中文记忆混在一起，读起来像另一个人 |
| 当时不在场 | 人不在场就不可能记住这件事。挡的是「AI 顺手给上一个场景的人写记忆」 |
| 超过 60 字 / 一回合超过 3 条 | 记忆会累积，单条太长、条数太多会稀释 prompt 里真正重要的信息 |

**人称归一化而非拒收。** 实测模型会写「记得**他**刚来时想家」。
注入 prompt 后是「你（这个 NPC）对玩家的了解：· 记得他刚来时想家」，
「他」会被读成另一个人。代码在写入前把开头的「记得他/她」改成
「记得你」——**改写比拒收宽容**，符合「世界层宽容」原则：
NPC 不会因为系统的人称规范没写好而失忆。只改开头，因为句中出现的
「他」可能指别人（「记得他妈妈做的茶」里的「他」指玩家）。

**产出率实测（12 样本 × 2 轮）：**

| 输入类型 | 产出率 | 判据 |
|---|---|---|
| 值得记（表露情绪/做出选择/具体事件/说起打算） | 70~85% | 下限 65% |
| 不值得记（寒暄/问价/常规交易/道谢） | 0% | 上限 20% |

**教训**：单轮 6 样本的噪声可达 ±17%（同一条用例在 3 轮里各命中 2 次，
但单轮可能两条都落空）。用单轮结果卡门槛会周期性误报，
把人骗去改本来正确的 prompt。测试必须**聚合多轮**。

**测试用例本身也会错。** 早期有一条「把伞落在便利店柜台」放在宿舍场景，
Sam 根本不在场，模型正确地没写，却被算成失败——
**测试用例设计错了，会让人去改本来正确的代码。**

## 五、状态机与流程

### 5.1 玩家移动流程

```
回合结束，AI 回应呈现完毕
        │
        ▼
UI 显示可达地点列表（由 connections 计算，非固定"下一关"）
        │
        ▼
玩家选择目标地点
        │
        ▼
代码结算：
  1. time += location.travel_cost
  2. 检查跨日 / 跨时段
  3. 判定新地点是否在营业时段内
  4. 判定进入深度（见 5.5）
        │
        ▼
按深度生成开场（或跳过 AI 调用）
```

**核心变化：切换不再是"系统判定你完成了，请前往下一关"，而是"我决定去哪"。** 这是消除关卡感的根本机制。

### 5.2 地点内回合流程

```
玩家输入（话语 / 动作）
        │
        ▼
代码构造上下文：
  世界状态 + 地点卡（含感官细节 + 当前时段变体）
  + NPC 卡（性格 + 说话方式 + 印象标签 + 记忆）
  + 最近事件 + 主线事实状态 + 信息槽位状态
        │
        ▼
AI 生成 → { narration, npc, feedback, world_changes }
        │
        ▼
代码校验 world_changes（见 5.6）
        │
        ▼
事件流 append（唯一真相来源）
        │
        ▼
呈现（打字机 / 双语旁白 / 反馈面板）
```

### 5.3 主线节点判定

**核心原则：判定基于世界事实，不基于对话质量。**

```
玩家说得好说得差，只要信息传达到、文件带齐，事实就成立。
```

**三条好处：**

| 好处 | 说明 |
|---|---|
| 不变成猜谜 | 不存在"必须说出某句魔法台词" |
| 天然宽容 | 现实中办事员会帮人补全信息、会追问、会确认 |
| 符合工程纪律 | 状态由代码管理，AI 只在规则内生成 |

**判定逻辑：**

```
节点完成 ⟺ 该节点全部 requires 条件满足
           ∧ 玩家位于指定 location
           ∧ 全部 requires_items 在背包里
           ∧ （若有 window）当前时间在窗口内
           → grants_facts 写入
```

**「不基于对话质量」不等于「不需要交互」。** 这一点在实现时才变得清楚，值得单独说明：

节点不会因为玩家走进房间就自动完成——那样整条主线会退化成走地图。实际分工是：

```
AI 观察到事情确实发生了（材料递过去了、对方确认了）
        │
        ▼  提议 set_fact
判定器检查地点、前置事实、随身物品、窗口
        │
        ▼  全部成立才写入
```

所以即使玩家说「我上周已经办过了」，AI 附和她写入事实，判定器也会因为玩家不在注册处、或材料没带而拒绝。**AI 是传感器，判定器是权威。**

#### 检查顺序

顺序不是随意的，按「玩家最需要知道的那一条」排：

| 优先级 | 状态 | 为什么排在这里 |
|---|---|---|
| 1 | `DONE` 已完成 | 已完成的不用再解释 |
| 2 | `WRONG_LOCATION` 人不在这里 | 玩家能立刻行动 |
| 3 | `OUTSIDE_WINDOW` 不在办理时间 | 玩家能立刻行动（等一会儿） |
| 4 | `MISSING_FACTS` 前置步骤没完成 | 需要回忆或返回，成本更高 |
| 5 | `MISSING_ITEMS` 材料没带 | 同上 |
| 6 | `AVAILABLE` 可办 | 无 |

先报地点而不是先报材料，是因为玩家站在宿舍时会以为「先把材料凑齐再去」，凑齐了跑一趟才发现还要先做前置——白跑。**先告诉他站错地方，他才知道该先移动。**

#### 事实只能由判定器写入

**判定器是 `facts` 进入玩家状态的唯一入口。**

阶段 A 的实现里，前端 `applyWorldChanges` 自己检查白名单就写入事实。这个设计有个致命缺陷：AI 说「她说你已经办好了」，事实就变成 true 了——玩家可能根本不在场、材料也没带。

现在改为：前端不再写任何事实，AI 的 `world_changes` 全部送交 `/api/judge` 裁决。规则只有一份实现，在前端复制一份必然漂移。

**拒绝不可静默。** 每条被拒绝的变更都带人话原因，记入日志。这是排查「AI 说办好了但世界没变」的唯一线索。

### 5.4 错过截止：软后果机制

**设计陷阱：** 若错过真的毫无后果，时钟会退化为装饰，玩家很快学会忽略它。

**解法：区分硬后果与软后果。**

| | 硬后果（不要） | 软后果（要） |
|---|---|---|
| 表现 | 错过 → Game Over / 重来 | 错过 → 世界记住这件事 |
| 对玩家的影响 | 惩罚，尤其惩罚正在艰难组织英文的人 | 世界承认你的行为 |
| 剧情走向 | 中断 | 分叉：多一个"解释与请求通融"的场景 |

**机制：**

```
时间推进越过 deadline
        │
        ▼
代码标记 mainline.missed = true（不中断游戏，不显示失败）
        │
        ▼
世界进入「错过状态」：
  1. 相关 NPC 上下文注入 missed 标记
  2. 地点状态变化（注册处贴出"逾期注册请至 Student Centre"）
  3. 生成新场景：解释原因 + 请求通融
  4. 激活 soft_paths 补救路径
```

#### 实现细节：两个容易做错的地方

**① 标记存在玩家状态上，不存在世界定义上。**

`Mainline` 是静态世界定义的一部分，被所有存档共享。把 `missed` 写在那里等于「一个存档逾期，所有存档都逾期」。正确位置是 `PlayerState.mainline_missed`。

**② `missed` 是「标志位 or 时间判断」的组合，不是纯标志位。**

标志位只在判定器跑过之后才写入，但进度查询会被多条路径调用（`/api/world`、`/api/move`、`/api/judge`）。只读标志位的话，一份时间已越界的存档在 UI 上会显示「未逾期」，直到玩家碰巧做了一次会触发判定的动作——**同一份状态，两种说法**。

所以 `mainline_progress` 里的 `missed` 恒等于：

```
player.mainline_missed or player.time.is_after(deadline)
```

**③ 逾期之后窗口不再拦截。**

这是最容易写错的一条。若 `OUTSIDE_WINDOW` 在逾期后继续生效，RTS Check 就变成一个「窗口过了就永远做不了」的节点——**死胡同**，直接违反 8.2，而且游戏不会告诉玩家为什么卡住。

现实中的处理也不是「办不了」，而是「可以办，但要先说明原因」。所以判定器在 `mainline_missed` 为真时跳过窗口检查，把难度交给对话：玩家必须解释自己为什么逾期。**惩罚从「做不了」转成「要多说几句话」，这正是我们想要的练习场景。**

**实证支撑：** 真实的英国大学制度正是这样运作的。注册截止后只有特殊情况才能注册，学生需联系 Student Centre **说明原因**，由院系评估（[Greenwich 官方答复](https://studentcentre.gre.ac.uk/knowledgebase/article/KA-09301/en-us)）。**"错过不惩罚"与真实制度天然吻合**，而且它创造了更好的练习场景——道歉、解释、请求通融，恰恰是真实生活里最难也最需要的表达。

**压力感由世界施加，不由 UI 施加。** 玩家可以完全无视主线去闲逛。正确的压力方式：

| ✅ 世界施加 | ❌ UI 施加 |
|---|---|
| 室友问"你注册了吗？" | 弹窗提醒"主线任务待完成" |
| 导师办公室门上贴着截止日期 | 倒计时数字闪烁 |
| 便利店公告栏有注册处传单 | 任务列表标红 |

**真实的硬后果是 reported to UKVI**（学校必须上报未注册学生）。游戏里不使用它，但可作为世界背景由 NPC 提及——压力感有了，惩罚不发生。

### 5.5 地点重入分级

**问题：** 玩家反复进同一家便利店，不能每次重播完整开场。

**方案：进入深度分级 + 地点状态持久化。**

| 进入次数 | 开场处理 | AI 成本 |
|---|---|---|
| 首次 | 完整开场：感官细节 + NPC 介绍 + 开场白 | 1 次调用 |
| 2~3 次 | 简短：1 句旁白说明当前状态 | 1 次轻调用 |
| 4 次以上 | 极简：一句环境提示，NPC 等玩家先开口 | **0 次调用** |

**判据：`f(进入次数, 距上次进入的时段数)`。** 刚出去又进来几乎无变化；隔了三天，世界该变了。

**关键：详细程度由代码决定，不由 AI 决定。** 这是成本控制的核心——把"要不要生成"的决定权留在代码层。

**地点保存"上次离开时的状态"：** 离开咖啡馆时咖啡师在忙，回来时她可能忙完了；上次把伞落在便利店，这次 Raj 会递给你。

### 5.6 状态变更校验

**核心约束：AI 返回的 `world_changes` 只是「提议」，不是事实。代码校验通过后才写入。**

这继承现有工程纪律——"程序决定是否接受状态变更，不能直接信任 AI 返回的任何状态修改"（[`产品文档.md`](产品文档.md) 7.2）。

**校验规则：**

| 提议类型 | 校验内容 | 拒绝示例 |
|---|---|---|
| `set_fact` | 事实名必须在 `facts` 白名单内；前置条件必须已满足 | AI 直接提议 `bank_account_opened: true`，但玩家没有在读证明 |
| `add_item` | 物品必须存在于世界物品表；必须能说明来源 | AI 凭空给出"学生证"，但玩家没去过注册处 |
| `set_location` | **一律拒绝**——移动只能由玩家发起 | AI 自作主张把玩家移动到银行 |
| `set_time` | **一律拒绝**——时间只由移动结算推进 | AI 说"天色已晚"就跳时段 |
| `update_npc` | NPC id 必须存在；印象标签不得包含对英语水平的评价 | AI 写入"这个人英语很差" |

**两条最重要的拒绝规则：**

1. **AI 不得移动玩家。** 移动是玩家的主动权，这是消除关卡感的核心机制（见 5.1）。若允许 AI 移动玩家，等于把刚交出去的主动权又收回。
2. **AI 不得推进时间。** 时间只被移动消耗（见 4.6）。若允许 AI 跳时段，玩家会困惑"为什么时间突然跳了"。

**校验失败的降级策略：** 丢弃该条提议，保留其余合法部分，**不中断回合**。同时记录日志——校验失败率高，说明 prompt 的约束写得不够清楚，是调优信号而非崩溃点。

## 六、生成层规范

### 6.1 套路感的根因

**实证发现：** 当前实现中，NPC 的性格是空字符串（[`ai.ts:70-71`](../frontend/src/api/ai.ts)），后端把它拼进 prompt 时，AI 看到的全部信息是：

```
名称：便利店
地点：英国街角便利店
NPC：Cashier（）-
```

AI 不知道这个收银员是谁、多大年纪、什么口音、店里什么样子。**输入是抽象的，输出必然是抽象的。** 这不是 prompt 写得不好，是没东西可写。

### 6.2 五项改进

| 改进 | 说明 | 成本 |
|---|---|---|
| 场景卡写"具体的物"而非"抽象的类型" | 感官细节（光线/声音/气味/温度）、具体时间、具体的人 | 写作成本 |
| 旁白强制引用具体细节 | prompt 要求旁白必须包含场景卡中的一个具体感官细节，否则重写 | 极低 |
| 套话禁用词表 | 命中即重写 | 极低 |
| **统一开场与回合的 prompt** | 当前是两套（[`ai_engine.py:152`](../backend/ai_engine.py) vs [`ai_engine.py:25`](../backend/ai_engine.py)），导致 NPC 性格漂移 | 低 |
| **转场携带真实上下文** | 当前只传一句"玩家完成了「便利店」场景"（[`gameContext.tsx:497`](../frontend/src/state/gameContext.tsx)） | 低 |

**套话禁用词表（中英双语）：**

| 中文 | 英文 |
|---|---|
| 你注意到 | You notice that |
| 似乎 / 仿佛 / 好像 | It seems / as if |
| 空气中弥漫着 | The air is filled with |
| 不由得 / 不禁 | somehow / cannot help but |
| 这一刻 | in this moment |
| 某种 | a certain / some kind of |
| 让你感到 | makes you feel |

### 6.3 NPC 人设候选池（骨架固定，血肉随机）

**这是"持久世界"与"重玩价值"之间张力的解法。** 世界每次一样，第二次就腻了。

| 固定（骨架） | 随机（血肉） |
|---|---|
| 地点图与可达关系 | NPC 具体人设（每个角色位备 2~3 个候选） |
| 主线结构与角色位 | 天气、时段、当天突发事件 |
| 世界规则与常识 | 主线节点的走法变体（节点固定，路径随机） |
| NPC 的身份与职能 | NPC 的姓名、性别、年龄、口音 |

同一个"便利店老板"角色位，这次是五十四岁的 Raj，下次是三十出头刚接手的年轻人——世界结构不变，体验完全不同。**写作成本线性增长，收益是乘法的。**

### 6.4 上下文注入清单

| 注入项 | 来源 | 说明 |
|---|---|---|
| 世界规则与禁忌 | `world.rules` / `taboos` | 每次必注入 |
| 地点感官细节 | `location.sensory` | 全部注入（仅 5 条） |
| 当前时段变体 | `location.variants[slot]` | 按当前时段选一条 |
| NPC 性格与说话方式 | `npc.personality` / `speech` | 全部注入 |
| NPC 印象标签 | `npc.impression_tags` | 全部注入（上限 8） |
| NPC 记忆 | `npc.memories` | 全部注入（上限 12） |
| 主线状态 | `facts` + `mainline.missed` | 只注入"玩家已知"的部分 |
| 信息槽位状态 | 见 7.1 | 仅硬需求场景 |
| 最近事件 | 事件流 | 最近 8 条 |

**注意"玩家已知"的过滤：** `knowledge[]` 之外的主线信息不注入。否则 NPC 会说出玩家还不该知道的事。

## 七、硬需求场景设计

**硬需求场景**指需要具体信息才能推进的场景，最典型的是银行开户。

**风险：** 便利店买三明治，表达错了也能蒙混过关；但开户需要姓名、地址、护照、金额，信息缺失就是办不成。若 NPC 严格索要信息，就变成"英语考试"；若太宽松，又不像真的。

### 7.1 信息槽位机制

```yaml
required_slots:
  name: 已填
  address: 缺失
  share_code: 缺失
  proof_of_address: 缺失
  account_type: 缺失
```

**核心洞察（来自真实观察）：办事员的工作就是帮人补全信息。** 真实的银行开户不是表达考试，是**协作填表**。办事员会逐项索要、重复确认、指着表格问"是这个吗"。

**NPC 的角色是逐项索要缺失项。** 玩家表达不好时，NPC 会：

| 策略 | 示例 |
|---|---|
| 追问 | "Sorry, could you spell that for me?" |
| 猜测确认 | "So that's 12 Mill Road — is that right?" |
| 给选项 | "Is that a student account or a standard one?" |

**失败的定义不是"说不出来"，而是"槽位没填满"。**

### 7.2 世界层宽容 + 学习层严格

**这是本次设计中最重要的架构决策，影响整个反馈引擎。**

| 层 | 态度 | 作用 |
|---|---|---|
| **世界层** | 宽容：信息传达到就推进 | 不挫败玩家，符合"敢错氛围" |
| **学习层** | 严格：照常记录表达质量问题 | 保证学习效果，供复盘 |

**两层分离是这个问题唯一的正解。** 世界层宽容保证玩家不卡死，学习层严格保证不白练。

### 7.3 退路机制与提示依赖记录

玩家真的卡住时，NPC 可以指表格、给选项，玩家只需说 "Yes" / "This one"。

**这不是作弊，这是真实生活。** 但系统必须**记录"这次用了退路"**——正好喂给学习档案的"提示依赖程度"指标（[`产品文档.md`](产品文档.md) 6.3）。

**额外收益：** 该机制天然产生"请求重复"与"澄清"的练习机会——正是产品文档列出的薄弱环节（"不知道怎样自然地请求别人重复"）。

## 八、兜底规则

**反直觉规律：世界越自由，越需要兜底机制。** 现有线性走廊虽然生硬，但有隐藏优点——玩家不可能做出预料之外的事。引入地点图后，以下情况必然出现。

**好消息：大部分不需要调度器，简单规则表即可覆盖。**

### 8.1 已知情况与处理

| 情况 | 处理 |
|---|---|
| **越界行为**（如"我要抢银行"） | 世界规则声明这是日常向世界。NPC 自然反应（困惑、拒绝、转移话题），不评判、不惩罚、不出戏 |
| **无处可去** | 宿舍永远可达，作为兜底锚点。任何时候至少有一个可达地点 |
| **无关话题** | NPC 按自己身份回应，不强行拉回主线 |
| **反复进出** | 地点状态持久，第二次进入描述简短化（见 5.5） |
| **因果链死胡同** | 每个主线节点必须定义 `soft_paths`（见 8.2） |
| **玩家完全不动** | 原地等待 = 一个回合，世界推进一拍，可能有事发生 |

### 8.2 因果链不能有死胡同

**这是新引入的结构性风险。** 学生证 → 在读证明 → 银行开户，若玩家卡在 RTS Check，整条链断裂。

**硬性要求：每个主线节点必须定义至少一条 `soft_paths`。**

| 节点 | 软路径示例 |
|---|---|
| RTS Check 卡住 | 先找导师说明情况 / 联系 Student Centre 预约 / 让室友陪着去 |
| 在读证明拿不到 | 学生系统自助下载 / 找院系办公室 / 请导师写证明信 |
| 银行拒绝开户 | 换一家银行 / 先办基础账户 / 先解决地址证明 |

**"错过不惩罚"原则在这里必须贯彻到底**——任何环节都不能出现"玩家永久卡死"的状态。

### 8.3 预留：调度器的位置

**当前不做。** 仅当出现以下情况时引入轻量调度器（节拍表）：

- 玩家做出**改变世界状态**的事（如真的动手），规则表无法覆盖
- 回合 AI 反复生成与事实矛盾的内容
- 需要主动制造剧情张力（当前由主线截止自然提供）

**预留位置：** 架构图中的「游戏控制层」（[`产品文档.md`](产品文档.md) 第七章）已包含此职责，只是暂未实现。

## 九、存档与持久化

### 9.1 核心原则：事件流是唯一真相

**"选择保存时机"这个思路本身就是错的。** 世界状态比线性状态复杂得多，正确的做法是：

```
事件流 = 唯一真相来源（append-only，永不修改）
世界状态 = 重放事件流的结果（可随时重建）
```

**为什么这是对的：**

| 好处 | 说明 |
|---|---|
| 天然支持"退出后继续" | 重放即可，无需设计"存档点" |
| 天然支持调试 | 任何一局都能完整回放 |
| 天然支持学习档案 | 事件流本身就是学习数据 |
| 零新增概念 | 复用已有 `GameEvent[]` 模型（[`types/index.ts:26`](../frontend/src/types/index.ts)） |

### 9.2 三个具体决策

1. **保存粒度是"回合"，不是"场景"。** 现在场景是保存单位，改成回合后，玩家任何时候关窗口都不丢进度。
2. **只保存"已生效"的事件，不保存"展示中"的。** 继承现有原则（[`MVP开发规划.md`](MVP开发规划.md) 第六章第 3 条）——打断中途关掉程序，不会存下半句 NPC 台词。
3. **MVP 只存事件流，不做快照。** 10~20 分钟的会话重放完全够快。快照是性能优化，等真的慢了再加。

### 9.3 表结构（SQLite）

```
sessions   会话元数据 + 玩家档案
events     append-only 事件流，按 turn 排序
npc_memory NPC 印象标签与记忆（可从事物流派生，也可独立存）
```

## 十、内容生产规范

### 10.1 写作顺序

**顺序错了，返工成本极高。**

| 顺序 | 写什么 | 为什么是这个顺序 |
|---|---|---|
| 1 | **世界圣经**（一页纸） | 不先写它，后面每个地点都会不一致 |
| 2 | **地点卡**（8 个） | 感官细节 ×5、可达地点、时段变体、常驻 NPC |
| 3 | **NPC 卡**（6~8 个） | 身份、性格、说话方式、印象标签规则、人设候选池 |
| 4 | **主线节点**（4 个） | 节点固定，路径留变体，每个必须定义 soft_paths |

### 10.2 数据格式：YAML + Pydantic

**推荐方案：YAML 写内容 + Pydantic 校验 + 启动时校验。**

| 理由 | 说明 |
|---|---|
| **JSON 没有多行字符串** | 感官细节、NPC 性格、台词风格全是散文。JSON 里要写成 `"冷白灯管有一根在闪\n货架第三层空了一格"`——对内容作者是折磨 |
| **JSON 没有注释** | 要"分批写、边玩边补"，注释让你能留 TODO 和备注 |
| **中英混排可读性** | YAML 少一半标点噪音 |
| **Pydantic 已在用** | [`main.py`](../backend/main.py) 已是 Pydantic。同一套模型既校验 API 请求，也校验内容文件——**模型即代码，不会与文档漂移** |

**关键机制：启动时校验，不通过就报错。**

内容错误是"AI 表现奇怪"的头号原因——地点卡少一个字段，AI 会静默降级，你根本不知道哪里错了。**启动时炸掉，好过运行时悄悄变傻。**

**存放位置：内容放后端，前端通过 API 拉取。** 未来多世界、动态内容都需要后端；校验只做一次；改内容不用重新构建前端。

### 10.3 第一批范围

**只写 3 个地点 + 3 个 NPC + 1 条主线。**

这不是保守——**世界层是新技术，没验证前写得越多，返工越多。**

建议第一批：

| 类型 | 内容 |
|---|---|
| 地点 | 宿舍、便利店、注册处 |
| NPC | 室友、Raj（便利店）、注册处职员 |
| 主线 | 仅 `enrol_online` → `rts_check` 两个节点 |

## 十二、分期实施路径

| 阶段 | 内容 | 可验证产出 |
|---|---|---|
| **阶段 A · 地基** | 世界/地点/NPC 数据模型 + YAML 加载与校验 + 状态模型重写 + "离开"变玩家动作 + 转场携带真实上下文 | 3 地点 + 3 NPC 可自由移动，转场不再生硬 |
| **阶段 B · 世界活起来** | 世界时钟 + NPC 印象标签与记忆 + 主线判定与截止 + 软后果机制 | 一条主线可走完，错过截止产生新场景 |
| **阶段 C · 血肉随机** | NPC 人设候选池 + 天气/时段随机 + 节点走法变体 | 同一世界两次游玩体验不同 |
| **阶段 D · 持久化** | 事件流存档 + 退出续玩 + 学习档案对接 | 关掉程序再打开可继续 |
| **阶段 E（预留）** | 调度器 | 仅在阶段 A~D 暴露兜底缺口时启动 |

**阶段 A 的产出对后续所有方案都是公共资产**——这是为什么它值得先做，而不是先纠结架构。

**验收标准（阶段 A）：**

1. 玩家可在地点图自由移动，"离开"由玩家发起
2. 转场旁白能引用上一场景的真实事实（而非通用套话）
3. 同一地点二次进入不再重播完整开场
4. 内容改 YAML 文件后重启即生效，无需改代码
5. 内容文件字段缺失时启动即报错

**验收标准（阶段 B · 主线判定器部分）：**

| # | 标准 | 怎么验 |
|---|---|---|
| 1 | 站在错误地点时，事实**不会**被写入 | 宿舍里说"我办好了 RTS"，判定器返回 `WRONG_LOCATION` |
| 2 | 材料没带齐时，事实**不会**被写入 | 注册处但没带护照，返回 `MISSING_ITEMS` 并说明缺哪一份 |
| 3 | 条件全部满足时，事实被写入且节点标记完成 | 注册处 + 带齐材料 + 前置已完成 → `AVAILABLE` → `DONE` |
| 4 | 拒绝必须带人话原因 | 每个非 `AVAILABLE` 状态都有可读的 `reason_zh` |
| 5 | 越过 deadline 后标记逾期，但**节点仍可办** | 逾期后 `OUTSIDE_WINDOW` 不再拦截，返回 `AVAILABLE` |
| 6 | 逾期后 prompt 能告诉 AI 该演什么 | `build_mainline_context` 输出逾期提示与 soft_paths |
| 7 | AI 提议的非法变更被逐条拒绝并记录 | `apply_changes` 返回 `rejected` 列表 |

第 5 条是最容易做错的一条——写成「窗口过了就锁死」会让玩家永久卡在 RTS Check，直接违反 8.2。

| 11 | **地点重入分级 + 状态持久化** | 避免重复开场；AI 成本由代码控制 |
| 12 | **硬需求场景用信息槽位机制** | 真实办事是协作填表，不是表达考试 |
| 13 | **世界层宽容 + 学习层严格** | 世界层保证不卡死，学习层保证不白练 |
| 14 | **事件流为唯一真相，每回合保存** | 无需设计存档点；复用已有模型 |
| 15 | **YAML 写内容 + Pydantic 启动时校验** | 散文可读性 + 注释支持 + 模型即代码 |
| 16 | 关系度用印象标签，不用数值 | 数值会诱导刷分，标签本身就是 prompt |
| 17 | 关系度不由英语表达质量驱动 | 违背"NPC 不惩罚表达"的核心原则 |
| 18 | 每个主线节点必须定义 soft_paths | 因果链不能有死胡同 |
| 19 | **判定器是 facts 的唯一入口，AI 只是传感器** | 前端各写一份校验必然漂移；AI 说"她办好了"不等于世界真的办了 |
| 20 | **逾期后窗口不再拦截，改为在对话里要求解释** | 锁死窗口 = 死胡同，违反 8.2；现实中也是"可以办，但要先说明原因" |
| 21 | **`missed` 存 PlayerState，且为「标志位 or 时间判断」** | Mainline 是共享定义，存那里会串档；只读标志位会让同一状态出现两种说法 |
| 22 | **判定器与校验器合并为同一模块** | 两者回答同一个问题，分开写优先级顺序迟早分叉 |
